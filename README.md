# 夜班接驳车末班核定

给夜班通勤协调员用的 Web 工具，包含两个相互配合的功能：

1. **末班核定**：输入时刻表首页 URL、上车站、下车站、最早出门与到岗截止的
   日期时间，自动翻页抓取两站时刻表，按**车次号 + 停站顺序**配对，只保留
   “发车不早于出门、到站不晚于截止”的班次，给出**发车最晚的一班**及两站来源。
2. **停运公告查询**：输入运营方公告首页 URL 与服务日期，自动翻页抓齐全部
   停运公告（公告编号、车次号、生效起止日期、原页地址），列出**当日停运车次
   及公告依据**，并用 SQLite 按来源保存最近一次完整抓取批次，避免把已停班次
   误报给员工。

## 停运公告查询

页面入口：顶部导航「停运公告查询」，或直接访问 `/notices/`。

- **分页抓取**：公告首页即第 1 页，沿 `a.next-page` 逐页抓取直到没有下一页
  （50 页上限、循环链接保护）；表头支持 公告编号 / 车次号 / 生效起始日期 /
  生效截止日期 等常见列名别名。
- **当日筛选**：按服务日对每条公告的生效起止闭区间判断，列出当日生效的
  停运车次与依据（含公告编号与记录所在分页的原页地址）。日期文本无法解析
  （如“即日 / 另行通知”）的公告不参与停运判断，单独列入“需人工核对”区。
- **批次存储（SQLite）**：按公告来源 URL 保存批次，采集时间一并记录：
  - 只有**全部分页取齐**后，才在同一事务内写入新批次并删除该来源旧批次，
    因此重查同一来源是**替换而非叠加**，不会出现新旧公告混在一起；
  - 任一页抓取失败时，只记录失败批次（失败页地址 + 错误信息），**不写任何
    公告明细**，旧完整批次原样保留，页面同时标明“依据的是上次完整批次”和
    失败分页；
  - 某来源**从未成功采集**时，页面明确提示不能据此断言“当日无停运”。
- 数据库路径由环境变量 `NOTICE_DB_PATH` 配置，默认 `app/data/notices.sqlite3`；
  Docker Compose 用命名卷 `notice-data` 持久化。

## 末班核定功能要点

- **分页抓取**：从首页的站点链接（`a.station-link`）找到两站第 1 页，沿
  `a.next-page` 逐页抓取，直到没有下一页（50 页上限、循环链接保护）。
- **配对规则**：两站记录车次号相同，且上车站停站顺序早于下车站才视为同一行程。
- **服务日区分**：按车次**始发服务日**标注工作日（周一至周五）/ 周末（周六周日）/
  每日；查询时按时间窗覆盖的每个始发日分别判断是否运行。
- **24:xx 跨日时刻**：`24:25`、`25:10` 等按“始发服务日零点 + 时间差”换算为真实
  日期时间；若下车站时刻（如 `01:00`）早于上车站发车（如 `23:50`）且未用 24 小时
  制书写，自动按次日处理。
- **异常提示**：
  - 任一分页抓取失败 / 表头缺列 / 链接循环 → 提示“无法核定末班”，且不展示不可信结论；
  - 车次缺停站顺序、缺关键时刻、两站服务日标注不一致、下车站无该车次记录 →
    逐条告警；若仍有其他完整班次，正常给出末班，告警与答案同时展示。
- 结果页展示末班车次、服务日类型、两站实际到发时间与原始时刻、两站来源 URL，
  以及时间窗内全部可选班次。

## 目录结构

```
.
├── app/                  # 末班核定 + 停运公告 Flask 应用（端口 5000）
│   ├── commuter/
│   │   ├── times.py      # 纯逻辑：时刻解析、服务日、配对核定（可单测）
│   │   ├── scraper.py    # requests + BeautifulSoup 时刻表分页抓取
│   │   ├── notices.py    # 纯逻辑：公告日期解析、生效区间与当日筛选
│   │   ├── notice_scraper.py  # 停运公告分页抓取
│   │   ├── notice_store.py    # SQLite 批次存储（完整替换 / 失败隔离）
│   │   ├── notices_views.py   # /notices/ 公告查询路由
│   │   ├── app.py        # Flask 路由与表单校验
│   │   └── templates/    # index.html（末班核定）、notices.html（公告查询）
│   ├── tests/            # 单元 / 端到端冒烟测试（共 44 个）
│   ├── Dockerfile
│   └── requirements.txt
├── example-site/         # 本地示例时刻网站（端口 5001）
│   ├── app.py            # 含分页、24:xx 跨日、工作日/周末、缺记录、500 故障站，
│   │                     # 以及跨页公告 /notices/ 与断页公告 /notices-broken/
│   ├── Dockerfile
│   └── requirements.txt
└── docker-compose.yml
```

## 用 Docker Compose 启动（推荐）

```bash
docker compose up --build
```

- 示例时刻网站：<http://localhost:5001/>
- 末班核定应用：<http://localhost:8000/>

在核定页面填写：

| 字段 | 示例值 |
| --- | --- |
| 时刻表首页 URL | `http://example-site:5001/`（容器间用服务名访问） |
| 上车站 | `滨河园区` |
| 下车站 | `中央厂区` |
| 最早出门 | `2026-11-11 22:00` |
| 到岗截止 | `2026-11-12 02:00` |

> 但核定应用运行在容器内，抓取 URL 必须填容器网络可达的
> `http://example-site:5001/`。

## 本地直接运行（不用 Docker）

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r app/requirements.txt

# 终端 1：示例时刻网站
cd example-site && python app.py            # http://localhost:5001

# 终端 2：核定应用
cd app && flask --app commuter.app run      # http://localhost:5000
```

此时首页 URL 填 `http://127.0.0.1:5001/`（或 `http://localhost:5001/`）。

在「停运公告查询」页填写（容器内用服务名访问示例站）：

| 字段 | 示例值 |
| --- | --- |
| 公告首页 URL | `http://example-site:5001/notices/` |

## 试一下异常场景

- **缺记录**：示例数据里 N206 在「中央厂区」没有停站记录，任意
  滨河园区→中央厂区查询都会看到黄色数据告警，末班仍由 N205 等完整数据核定。
- **分页失败**：上车站填「故障北站」，其第 2 页返回 HTTP 500，页面显示红色
  “无法核定末班”，并标明失败的分页地址。
- **周末 vs 工作日**：把时间窗放到周六晚上（如 2026-11-14 22:00 至
  2026-11-15 02:00），结果中只会出现“每日”和“周末”班次。
- **公告断页**：公告首页填 `http://example-site:5001/notices-broken/`，
  其第 2 页返回 HTTP 500。若该来源从未成功采集，页面明确提示“不能据此判断
  当日无停运”；若此前已成功采集过，则保留并标明上次完整批次与失败页，
  部分新公告不会混入旧结果。
- **日期无法解析**：正常公告源中的 GG-2026-0006 生效日期写成“即日 / 另行通知”，
  会进入“需人工核对”区，不参与自动停运判断。

## 适配真实时刻表站点

抓取器对页面结构的约定（见 `app/commuter/scraper.py`）：

1. 首页上站点链接带 `class="station-link"`，文本为站点名；
2. 站点页有 `<table>`，表头包含 车次号 / 停站顺序 / 站点 / 时刻 / 服务日
   （支持常见别名，如“站序”“班车”“到时”等，见 `_HEADER_ALIASES`）；
3. 翻页链接带 `class="next-page"`；
4. 服务日列出现“工作日/平日/weekday”“周末/双休/weekend”“每日/daily”等字样。

结构不同的站点只需调整 `scraper.py` 中的选择器与表头别名，核心核定逻辑
（`times.py`）无需改动。

## 适配真实公告站点

公告抓取器（`notice_scraper.py`）对页面结构的约定：

1. 公告首页即分页第 1 页，含一张 `<table>`；
2. 表头包含 公告编号 / 车次号 / 生效起始日期 / 生效截止日期
   （支持“编号 / 文号”“班车 / 班次”“开始日期 / 停运开始”等别名，
   见 `_HEADER_ALIASES`）；
3. 翻页链接带 `class="next-page"`，最后一页没有该链接；
4. 日期支持 `2026-11-13`、`2026/11/13`、`2026年11月13日`、`20261113` 等写法；
   无法解析的日期文本会保留原文并转入人工核对，不会被静默当成无停运。

结构不同的公告站点只需调整 `notice_scraper.py` 的选择器与表头别名，
日期解析（`notices.py`）与批次存储（`notice_store.py`）无需改动。
